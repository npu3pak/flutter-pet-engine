Документ для контекста реализации. Задаёт объём, порядок, ссылки на
документы и критерии приёмки. Читать вместе с `AGENTS.md`.

## 0. Что уже сделано (не переделывать)

- Репозиторий `pet_engine` создан; есть `engine/`, `docs/`, `projects/`,
  `scripts/`, заготовки `demo/` и `scene_editor/`.

  `analyze` чист, 317 тестов зелёные.

  `migration.md`, `conventions.md`, `visual_testing.md`, этот ТЗ.
- Общий форк — отдельный репозиторий `pet_games/flutter_scene`; v1-проекты
  переподключены к нему и зелёные.
- Решения фазы 1 и валидации зафиксированы: `plan.md`, раздел 7.
- Уточнения API (ключи текстур, свет и качество, владение, `capture`,
  `ProjectStore`) внесены в `api.md`.

## 1. Цель и объём

Цель: построить движок нового поколения с API `SceneViewport` /
`SceneController` / `SceneNode`, перевести на него demo (примеры) и
scene_editor, поддерживать документацию.

Входит в объём:

1. **Движок (фаза 2)** — публичный API по `docs/api.md` поверх
   перенесённого v1-кода; поведение v1 сохраняется.
2. **demo (фаза 3)** — приложение-пример: все 48 фич example, документация
   кодом, визуальное тестирование, диплинки, снимки, perf.
3. **scene_editor (фаза 4)** — полный перевод редактора на API v2:
   документ и undo, панели, вьюпорт с picking/гизмо/оверлеями/слоями,
   ресурсы, просмотр моделей, разметка.
4. **Документация** — поддержание базы знаний в актуальном состоянии,
   журнал фаз в `plan.md`, запись отклонений и решений.
5. **Очистка (фаза 5)** — удаление старых фасадов из публичного экспорта и
   кода после миграции demo и редактора (список — `docs/api.md`, раздел 20).

Не входит:

- миграция `math_quest` и `mypet-game` (отдельные работы после приёмки v2);
- перенос форка внутрь `pet_engine` (финальный шаг, позже);
- изменения старых репозиториев (`pet_engine`, игры);
- фаза 6 (оптимизация производительности).

## 3. Правила работы

- Flutter master через FVM (`.fvmrc`); команды из каталога пакета.
- Коммиты — только по явной просьбе владельца; сообщения по-русски.
- `docs/features.md` — источник требований, `docs/api.md` — контракт.
  Расхождение — сначала правка документа, потом код.
- Приложения (demo, scene_editor) не импортируют `package:flutter_scene/...`.
- Конвенции `docs/conventions.md` не менять.
- Тесты без видеокарты; для вьюпорта предусмотреть подменяемый бэкенд.

Границы рабочего каталога:

- Работаем только внутри `pet_engine`; текущий подкаталог определяем
  через `pwd`. За пределы репозитория не выходим.
- Не читать и не менять соседние каталоги: `../math_quest`,
  `../mypet-game` и прочие. Форк `flutter_scene` — внутри репозитория
  (`engine/third_party/flutter_scene`).
- Временные файлы — только `pet_engine/temp/`; `/tmp`, домашний каталог
  и файлы вне репозитория запрещены.
- Информация о плагинах, зависимостях и сторонних библиотеках (включая
  общий форк) — из интернета и официальной документации, а не из соседних
  каталогов.

### 4.10. Визуальные проверки по ходу работы (обязательно)

Агент проверяет demo сам, не дожидаясь владельца:

1. Staging из корня репозитория:
   `fvm dart run scripts/stage_app_assets.dart`; затем запуск:
   `cd demo && fvm flutter run -d macos --enable-flutter-gpu
   --enable-impeller`.
2. Сценарий: открыть фичу (диплинк или интерфейс), сделать **встроенный**
   снимок движковым механизмом (`SceneViewport.capture` + `saveScreenshot`);
   системный `screencapture` в агентской среде не работает и не нужен.
3. Анализ: проверить кадр на фуксию (потерянный ресурс), серые заглушки,
   пустоты (`analyzePlaceholders`/`analyzeFrameContent`).
4. Периодичность: после каждой группы фич demo и перед переходом к
   следующей фазе; при правках движка — хотя бы одна смоук-фича.
5. Журнал: `demo/visual_tests.json`; события `note` и `fixed` пишет агент,
   вердикт `ok` — только владелец.
6. Найденные дефекты исправляются по ходу; неисправленные фиксируются в
   журнале к финальной приёмке.

## 5. Приёмка

**Промежуточная (агент, по ходу работы):**

- после каждого подшага фазы 2 — `fvm flutter analyze` и
  `fvm flutter test` в `engine/`;
- после каждой группы фич demo — визуальная проверка на macOS по
  разделу 4.10;
- после этапов редактора — его тесты и визуальная проверка вьюпорта.

**Финальная (владелец, после всего v2):**

- выполняется один раз, когда готовы движок, документация, demo и
  scene_editor;
- владелец проходит demo по всем фичам, проверяет редактор и выносит
  замечания; вердикт `ok` ставит только владелец;
- до финальной приёмки работы по v2 не считаются завершёнными, миграция
  `math_quest`/`mypet-game` не начинается.

**Критерии готовности к финальной приёмке:**

1. `fvm flutter analyze` и `fvm flutter test` зелёные в `engine/`, `demo/`,
   `scene_editor/`.
2. Публичный экспорт `pet_engine` — только API из `docs/api.md`;
   старые фасады удалены.
3. В `demo/lib` и `scene_editor/lib` нет импортов `flutter_scene`.
4. Все визуальные самопроверки demo пройдены, открытые замечания
   перечислены в журнале.
5. Редактор сохраняет паритет со старым.
6. Документы актуальны, журнал фаз заполнен.

## 6. Риски и грабли

- **Тестовый шов вьюпорта без GPU** — спроектировать в подшаге 3 первым;
  без него остальные тесты упрутся в рендер.
- **Не сломать `engine/test`**: новый API добавляется рядом, старые фасады
  не трогаются до миграции demo и редактора.
- **Mirrored-X и порядок вершин билбордов** — не менять
  (`docs/conventions.md`).
- **FVM без `.fvmrc` молча ничего не делает** — в пакетах `.fvmrc` уже есть.
- **Утечки** — следовать правилам владения из `api.md` §16.1.
- **Дрейф копии v1**: старый движок заморожен; критичные фиксы переносить
  точечно.
- **Производительность**: demo и редактор проверять на macOS и устройстве.

## 8. Уточнения API, внесённые в документы

- **Ключи текстур:** списки — стемы; резолвер и `setTexture` принимают ключ
  с расширением или стем; в документе ключ с расширением (`api.md` §8).
- **Свет и качество:** `setShadows`/`setSsao` пишут в `QualitySettings`;
  `ModelLighting` — художественная подсказка (`api.md` §4, §5.5).
- **`capture`:** `Future<Uint8List>`, PNG; `pixelRatio` по умолчанию —
  вьюпорта, затем `devicePixelRatio` (`api.md` §2, §18).
- **`FaceRef.material`:** документный `ModelMaterial` (`api.md` §14).
- **Владение:** правила в `api.md` §16.1.
- **`ProjectStore`:** канонический путь записи моделей; `SceneResources` —
  только чтение (`api.md` §4, §16).

Отложено на реализацию (`api.md` §21): имя ресурсной сессии, полный набор
операций `GeometryBuilder`, состав `DeviceCapabilities`, пороги политики
качества, формулы слоёв неба, несколько камер на вид.
