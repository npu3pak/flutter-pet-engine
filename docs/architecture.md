# Архитектура pet_engine_v2

Документ описывает устройство нового движка: из чего он состоит, какие слои
существуют, какие зависимости допустимы и как код разделяется между простым
и оптимизированным профилями использования.

Статус: согласован в фазе 1. По мере реализации документ уточняется.

## 1. Назначение

`pet_engine_v2` — движок для трёхмерных сцен формата `model_v1` с публичным
API в стиле Flutter: виджет `SceneViewport` (один или несколько видов и
слоёв), контроллеры `SceneController`, `CameraController`,
`QualityController` и живая иерархия `SceneNode`.

Движок обслуживает четыре проекта:

- `demo` — приложение-пример: полный каталог возможностей, одновременно
  документация кодом;
- `scene_editor` — редактор сцен: документ, undo, picking, гизмо, оверлеи,
  слои;
- `mypet-game` — простая игра (миграция после приёмки v2);
- `math_quest` — сложная процедурная игра (миграция после приёмки v2).

## 2. Слои

```
┌──────────────────────────────────────────────────────────────────────┐
│ Приложения: demo, scene_editor (позже: mypet-game, math_quest)       │
│   SceneViewport(controller)                                          │
│   SceneController: ноды, камера, ресурсы, настройки, статус          │
│   SceneNode: BoxNode, SpriteNode, ModelNode, LightNode, MeshNode ... │
├──────────────────────────────────────────────────────────────────────┤
│ pet_engine_v2: публичный API                                         │
│   src/api/ — SceneViewport, SceneController, SceneNode, ввод, слои   │
├──────────────────────────────────────────────────────────────────────┤
│ pet_engine_v2: механизмы (перенесены из v1 и развиваются)            │
│   документ model_v1/project_v1, рендер-ядро (ModelRenderer,          │
│   материалы, csg), уровневый слой, навигация, частицы, скайбокс,     │
│   конвенции координат, ресурсы, качество картинки                    │
├──────────────────────────────────────────────────────────────────────┤
│ flutter_scene — общий форк, отдельный репозиторий                    │
└──────────────────────────────────────────────────────────────────────┘
```

Правило зависимостей: приложения зависят только от `pet_engine_v2`; типы
форка (`Scene`, `Node`, `Mesh`, `GeometryBuilder`, `SceneView`) наружу не
выходят. Исключение на время существования v2 — сам `scene_editor`, пока его
низкоуровневые части не переведены на API.

## 3. Состав пакета `engine/`

Пакет называется `pet_engine_v2`, публичный вход — `lib/pet_engine_v2.dart`.
Текущий состав (унаследован от v1, будет перерабатываться):

| Каталог | Содержимое |
|---|---|
| `src/api/` | новый публичный слой (появится в фазе 2) |
| `src/models/` | документ `model_v1`, конвертер легаси-чанков, загрузчик |
| `src/scene/` | рендер документа: `ModelRenderer`, csg, привязка к граням |
| `src/render/` | низкоуровневый фасад v1 (`EngineScene`, `EngineNode`, ...) |
| `src/engine/` | высокоуровневый фасад v1 (`GameScene`, `GameNode`, `GameCamera`) |
| `src/camera/` | контроллеры камеры, математика камеры |
| `src/level/` | уровневый слой: сетка, построение, запекание, загрузка |
| `src/navigation/` | источники навигации, планировщик, следование маршруту |
| `src/particles/` | частицы и погода |
| `src/dynamic/` | динамические объекты с временем жизни и пулом |
| `src/services/` | ресурсы: кэш текстур, glTF, хранилище проекта |
| `src/skybox/` | статический скайбокс |
| `src/engine_compat/` | координаты и материалы (конвенции) |
| `src/visual/` | снимки сцены для автотестов |

После фаз 2–4 слои `src/engine` и `src/render` либо станут внутренней
реализацией нового API, либо будут удалены. Решение принимается на фазе 1
(см. `migration.md`, раздел о старых фасадах).

## 4. Публичные понятия

### 4.1. `SceneViewport` — виджет

Виджет владеет тремя вещами, о которых приложение не думает:

1. **Размер.** Виджет сам измеряет свои размеры и сообщает их контроллеру
   (проекция, попадания, масштаб перетаскивания).
2. **Кадр.** Виджет сам ведёт тик: раз в кадр вызывает обновление
   контроллера (камера, динамика, билборды, подписчики кадра) и перерисовку.
3. **Ввод.** Виджет принимает события указателя и клавиатуры и передаёт их
   обработчику ввода; по умолчанию это управление камерой, приложение может
   подставить своё поведение.

Дополнительно виджет умеет: рисовать оверлеи поверх сцены, показывать
состояние загрузки, сообщать о нажатиях с координатами и лучом.

### 4.2. `SceneController` — контроллер сцены

Владеет:

- сессией ресурсов: открытие проекта, загрузка моделей, статус и прогресс,
  освобождение;
- сценой и реестром нод: добавление, удаление, поиск по идентификатору и
  типу;
- активным контроллером камеры;
- настройками картинки: качество, туман, сглаживание, масштаб рендера,
  тени, освещение;
- покадровым обновлением и списком подписчиков кадра;
- попаданиями и проекцией (экран ↔ мир);
- документом: текущая `ModelData`, если сцена загружена из документа.

Контроллер — `ChangeNotifier`: интерфейс может подписываться на изменения
статуса и состояния.

### 4.3. `SceneNode` — нода

Живой объект сцены. Общий базовый класс отвечает за:

- идентификатор, имя, видимость, прозрачность;
- признак `inScene` и ссылку на контроллер;
- трансформацию (положение, поворот, масштаб) в мировых координатах;
- материал: цвет, текстура, параметры шейдера;
- удаление со сцены и освобождение;
- уведомление слушателей об изменениях.

Наследники (закрытый набор, расширяется вместе с движком):

| Нода | Что представляет |
|---|---|
| `GroupNode` | контейнер для иерархии |
| `BoxNode`, `PlaneNode` | параметрические примитивы |
| `SpriteNode` | вертикальная карточка с текстурой (билборд или фиксированная) |
| `MeshNode` | произвольная геометрия (композиции игры, служебные построения) |
| `ModelNode` | объект документа `model_v1`; для glTF — живые трансформации и анимации |
| `LightNode` | точечный или направленный свет |
| `ParticleNode` | источник частиц/погоды |
| `SpriteFieldNode` | инстанс-поле спрайтов (трава) |
| `GroundFogNode` | стелющийся туман |
| `SkyboxNode` | статическая панорама за сценой |

### 4.4. Камера

Интерфейс `CameraController` уже существует в v1 и переносится: контроллер
владеет трансформацией камеры, проекцией и горизонтальным направлением
(для разворота билбордов). Реализации: свободный полёт, первый план, орбита,
фиксированная точка. Активный контроллер хранит `SceneController`; смена
контроллера сразу применяет проекцию и трансформацию.

### 4.5. Ввод

Ввод отделён от камеры: `SceneViewport` принимает события, а обработчик
ввода (`SceneInput`) решает, что с ними делать. Стандартный обработчик
управляет активной камерой; редактор подставляет свой (кнопки мыши, касания,
клавиатура, колесо). Приложение также может отключить стандартный ввод и
обрабатывать события само.

### 4.6. Качество

`QualityController` — отдельный контроллер производительности: определяет
графический бэкенд и возможности устройства, собирает статистику кадров
(`FrameTiming` и кадры вьюпорта), применяет настройки качества к
`SceneController` и при включённой адаптации меняет их по лестнице
(`renderScale → AA → SSAO → тени/каскады`) с гистерезисом, полом и потолком.
Замер и политика живут в движке; платформенные подсказки (например, режим
стабильной производительности на Android) применяет приложение.

Реестр возможностей, из которого выведен API, — `docs/features.md`;
подробные сигнатуры — `docs/api.md`.

## 5. Два профиля использования

**Простой профиль** (demo, игры):

```dart
final controller = SceneController();
await controller.open(source);
await controller.loadModel('model_2');

final marker = controller.add(SpriteNode(texture: texture));
marker.position.setValues(1, 0, 2);

SceneViewport(controller: controller);
```

Код читается сверху вниз, без знания о внутренностях рендера.

**Оптимизированный профиль** (scene_editor, math_quest):

- те же контроллер и ноды, но с доступом к слоям рендера и нескольким видам
  (основной вид, гизмо, оверлеи);
- произвольная геометрия (`MeshNode` + `EngineGeometry`/`PrimitiveBatch`);
- попадания по сцене и по граням объектов;
- переиспользование буферов и пулов вместо пересоздания нод;
- прямые подписки на кадр с известным порядком вызовов.

Различие профилей — не разные API, а разные точки входа в одном API.

## 6. Жизненный цикл

1. Создание контроллера.
2. `open(source)` — проект, модели, каталог ресурсов; контроллер сообщает
   статус и прогресс.
3. `loadModel(id)` или `loadModelData(data)` — содержимое сцены.
4. Встраивание `SceneViewport` в дерево виджетов — начинается кадр.
5. Работа приложения: добавление/изменение/удаление нод, смена камеры,
   настройки.
6. `dispose()` — остановка кадра, освобождение ресурсов.

Один контроллер может обслуживаться одним вьюпортом. Несколько контроллеров
(например, основная сцена и окно предпросмотра) сосуществуют независимо.

## 7. Проверяемость без видеокарты

Рендер требует GPU, поэтому логика отделяется от рендера:

- математика камеры, координат, попаданий, планирования — чистые функции;
- документ и уровни — чистые данные;
- у виджета вьюпорта предусматривается подменяемый бэкенд, чтобы
  тестировать тик, ресайз и ввод без GPU;
- визуальная проверка — отдельная методика (`visual_testing.md`).

## 8. Правила репозитория

- Приложения не импортируют `package:flutter_scene/...`; типы форка
  скрываются внутри движка.
- Документ `model_v1` остаётся единственным форматом сцены; редактор и игры
  сериализуют один и тот же документ.
- Конвенции координат и билбордов не меняются (`conventions.md`).
- Временные файлы — только в `temp/`.
